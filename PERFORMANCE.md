# Оптимизация 0.8.0

Сравнение с опубликованной 0.7.40. Оформление, правила подсчёта и формат сохранённых данных сохранены. Изменения охватывают лист, каталог персонажей, поле, фон расширения, отдельные вкладки и облачную панель ведущего.

## Измерения

Одинаковый синтетический сценарий: 20 персонажей, 20 хранилищ по 15 тегов у каждого, документ около 491 тысячи символов. Node.js/JSDOM на одном компьютере; время поиска — медиана пяти прогонов. Скрипт `tests/performance-bench.js` не обращается к сети и не использует пользовательские данные.

| Показатель | 0.7.40 | 0.8.0 |
| --- | ---: | ---: |
| 20 зачёркиваний в одном хранилище | 5358 мс | 2050 мс |
| Созданные при этом элементы | 27 460 | 1 440 |
| Сохранение соседней карточки в DOM | нет | да |
| 200 запросов активного персонажа | 1548 мс | 0,65 мс |
| 50 загрузок одного персонажа | 399 мс | 34 мс |
| Начальный JavaScript листа, без сжатия | 588 494 байта | 412 626 байт |
| Начальный JavaScript листа, gzip | 171 025 байт | 119 148 байт |
| Начальный JavaScript фона, без сжатия | 473 878 байт | 242 340 байт |
| Начальный JavaScript фона, gzip | 135 028 байт | 66 351 байт |

Размеры учитывают статические зависимости входной страницы production-сборки, исключая динамически загружаемые модули. Это размер кода, а не замер времени открытия комнаты или всех сетевых ресурсов. Время JSDOM не следует переносить на реальную комнату напрямую.

## Что изменено

- Проверенный список персонажей кэшируется до изменения исходной записи. Наружу возвращаются копии; изменение загруженного объекта без сохранения не меняет кэш. Внешние обновления и ошибки записи учитываются.
- Рюкзак и хранилища обновляются по отдельности. Соседние карточки, фокус и раскрытые области сохраняются. В обычных темах зачёркивание, вопросы, ромбы и Могущество обновляют существующие элементы; смена темника по-прежнему перестраивает содержимое.
- При вводе заметки измеряется только её текстовое поле. Полная проверка высоты остаётся при открытии разделов.
- Перемещение объекта на поле без изменения его данных не пересобирает каталог тегов и статусов калькулятора. Изменение версии, видимости, активного персонажа и эффектов ведущего обновляет каталог.
- Подписи источников на поле синхронизируются при изменении имени персонажа, а не при каждом сохранении листа.
- Тяжёлый генератор графики и разбор шрифтов загружаются при первом обращении к отрисовке карточек. Облако и трёхмерные кости остаются отдельными от начальной загрузки.
- Повторяющиеся запросы размера окна объединяются; уже выставленные ширина и высота не отправляются снова. Уменьшение при переносе карточки сохраняет последовательность операций.
- Одинаковые сохранения не создают лишние записи и сообщения между отдельной вкладкой и комнатой. После ошибки запись можно повторить.
- Обычная проверка облака читает только `revision`. При изменении загружается документ; первый вход и принудительное обновление читают его полностью. При изменившейся версии потребуется два запроса вместо одного. Сохранение неизменённого документа не увеличивает облачную версию. Права, конфликты и местный кэш сохраняются.

## Проверка и воспроизведение

215 автоматических проверок проходят, включая восемь новых проверок оптимизации. Проверены сохранение старых данных, переключение и передача персонажей, доступ игроков и ведущего, карточки на поле, быстрые отметки, облачные конфликты, отказ записи и отдельные вкладки. Production-сборка 0.8.0 успешна. Чтение одного столбца `revision` дополнительно проверено в настоящем Supabase под ролью authenticated в транзакции с откатом; схема и права базы не изменялись.

Для проверки отдельной сборки в PowerShell:

```powershell
npm run build -- --outDir ../optimization-build
$env:LITM_BUILD_DIR='../optimization-build'
node --test --experimental-test-isolation=none tests/*.test.js
node tests/performance-bench.js ../../optimization-build/
```

Без `LITM_BUILD_DIR` проверка манифеста использует опубликованную папку `docs`. До публикации она может относиться к предыдущему выпуску.

Измерения проведены локально. Новую версию ещё необходимо проверить в настоящей комнате после публикации, особенно перенос карточек, уменьшение окна и работу нескольких участников. Большой модуль трёхмерных костей сохраняется и загружается по требованию; предупреждение сборщика о его размере ожидаемо.
